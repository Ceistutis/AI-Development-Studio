## Antes de importar

1. Garanta que a v0.3 funcione na instância atual e registre seu output. Não use o briefing legado de teste de triagem para gerar issue real.
2. Crie o schema do ledger em banco PostgreSQL durável; configure **credencial Postgres** no n8n com `SELECT`, `INSERT` e `UPDATE`, sem `DELETE` e sem DDL. Não use a base interna do próprio n8n como armazenamento de aplicação.
3. Importe `ads-notion-github-controlled-v0.4.json` como workflow novo, **desativado**. Associe as credenciais aos seis nós HTTP do Notion, aos dois nós HTTP do GitHub e aos cinco nós PostgreSQL. Confira o total na versão instalada antes de qualquer execução.
4. Nas credenciais usadas nos nós `HTTP Request`, permita **somente** `api.notion.com` para Notion e `api.github.com` para GitHub. Não compartilhe tokens no código, workflow exportado ou commits. O Postgres usa credencial própria.
5. Execute primeiro com `ENABLE_REAL_WRITES = false` no nó **Selecionar briefing aprovado**. Saída esperada: `V0_4_DISABLED`, sem acesso ao ledger ou escritas externas.
6. Crie **um briefing novo, dedicado ao teste v0.4**, com `Status=Aprovado`, campos essenciais completos, repositório autorizado e `Issue GitHub` vazio. Deixe outros briefings aprovados já concluídos vinculados a seus links. Se houver mais de um não vinculado, o fluxo falha fechado. Opcionalmente restrinja explicitamente a um UUID editando `TARGET_NOTION_ID` no mesmo nó.
7. Somente quando estiver pronto para criar **uma issue real de teste**, altere `ENABLE_REAL_WRITES = true` na **cópia do workflow no n8n**, mantendo o JSON do GitHub seguro/desativado. Confira as credenciais, o briefing, o status e o marcador antes de acionar `Manual Trigger`. Não habilite schedule/webhooks.

## Fluxo de escrita

1. Ler Notion e recusar execução se `has_more=true` ou mais de um briefing elegível (falta paginação deliberadamente, falha fechada).
2. Exigir `Status=Aprovado`, campos essenciais e repo permitido. O trigger é manual; o indicador `ENABLE_REAL_WRITES` funciona como *arm switch* adicional.
3. Inserir a reserva durável por chave única `(repository, notion_id)`. Somente a execução que obteve reserva nova pode seguir para criação. Estados anteriores `RESERVED`, `CREATE_STARTED` e `LINKED` não recriam issue.
4. Pesquisar o GitHub por `NOTION_BRIEFING_ID:<uuid>`; recusar resultados incompletos ou correspondências existentes. Atenção: a pesquisa sofre atraso de indexação; a proteção principal é o ledger.
5. Reconsultar a página Notion e confirmar que aprovação, link vazio e `last_edited_time` permanecem inalterados.
6. Persistir `CREATE_STARTED` **antes** de emitir o único POST de criação ao GitHub. Sem retries automáticos nesse POST.
7. Validar a resposta; persistir URL e número da issue no ledger como `CREATED`; atualizar `Issue GitHub` no Notion; marcar `LINKED`.
8. Em nova execução, `CREATED` reaproveita a URL persistida e tenta apenas finalizar o vínculo no Notion, **sem POST ao GitHub**. Se o campo Notion já contiver o mesmo link, é seguro repetir seu PATCH e finalizar o ledger (veja `TARGET_NOTION_ID`).

## Estados e recuperação

| Ledger | Significado | Comportamento automático |
| --- | --- | --- |
| `RESERVED` | Reserva existe, sem prova de criação iniciada | **HALT**; exige análise |
| `CREATE_STARTED` | Pode ter sido enviado o POST (resposta perdida) | **HALT**; não repetir POST |
| `CREATED` | URL da issue persistida, Notion possivelmente não atualizado | **RECOVER_LINK**; PATCH no Notion, depois `LINKED` |
| `LINKED` | Issue e Notion vinculados | **HALT**; não duplicar |

**Cenário crítico:** o GitHub recebe o POST, mas o n8n perde a resposta ou falha antes de persistir `CREATED`. A execução fica em `CREATE_STARTED` e **não tenta criar outra issue**. Um operador deve procurar a issue no GitHub (incluindo listagem/paginação e conferência do marcador, não apenas busca textual), confirmar título, corpo e número e, se encontrada, reconciliar o ledger para `CREATED` com URL/número reais. Nunca limpar a reserva nem repetir o POST por suposição. Uma ausência de resultados no Search não prova que o POST não chegou ao GitHub.

**Falha após PATCH Notion, antes de `LINKED`:** o campo `Issue GitHub` já pode estar preenchido. Informe `TARGET_NOTION_ID` com o UUID desse briefing na cópia importada, execute novamente e confira que o ledger estava `CREATED`. O processo reconhecerá o mesmo URL, repetirá o PATCH idempotente e marcará `LINKED`. Se ledger já estiver `LINKED`, será bloqueado sem duplicação.

**Conflitos:** se o Notion contiver link diferente do ledger, pare e investigue manualmente. Não sobrescreva. Se alguém editar o briefing/revogar a aprovação antes da criação, o workflow recusa o POST. Se o resultado de uma query crítica não for retornado, trate a execução como inconclusiva; confira o estado SQL antes de agir.

Consulta somente leitura para diagnóstico:

```sql
SELECT repository, notion_id, status, issue_url, issue_number, created_at, updated_at
FROM ads_issue_ledger
ORDER BY updated_at DESC;
```

Um procedimento de reparo deve ser revisado por uma pessoa e executar alterações SQL com parâmetros reais verificados, jamais gerar valores hipotéticos ou apagar reservas automaticamente.

## Limitações conhecidas

- O workflow não foi importado nem executado na instância n8n por este assistente. Compatibilidade do nó Postgres `typeVersion:2.5` e expressões deve ser confirmada.
- Rejeita leitura Notion paginada e múltiplos briefings elegíveis, propositalmente para o piloto. Uma v0.4.x deve incluir paginação, seleção explícita sem edição do nó e alertas operacionais.
- A chave única protege execuções que cooperam usando **o mesmo** ledger; não oferece transação atômica distribuída Notion/GitHub/Postgres, nem impede operações manuais fora do fluxo.
- Em caso de resposta HTTP ambígua, escolhemos **parada segura com reconciliação humana**, nunca retry de criação. A segurança depende de retenção do ledger e backups regulares.
- Uma alteração externa nos campos do Notion durante o curto intervalo entre verificação e POST ainda é teoricamente possível (TOCTOU). Exigir execução de teste manual com mudanças controladas.
- Não habilitar para briefings de clientes antes de completar a checklist de QA e definir uma política de auditoria.
